Citation: Jin, Y., Xu, Y., Zhu, J., Yang, Y. MemSlides: A Hierarchical Memory Driven Agent Framework for Personalized Slide Generation with Multi-turn Local Revision. arXiv preprint, 2026. https://arxiv.org/abs/2606.17162v1

## What this paper is about

Slide-generation agents can now produce polished decks, but they don't remember that a given user always prefers a particular layout style for academic talks versus business pitches, and when a user asks for one small local fix ("change this number on slide 5"), most systems re-read or re-generate large parts of the deck, risking unwanted drift elsewhere. MemSlides addresses both problems together: a three-part memory system (a persistent cross-job user profile, a session-scoped working memory for the current revision, and a reusable tool-execution memory) paired with a scoped, patch-based local-edit mechanism that touches only the smallest necessary region of the deck instead of regenerating it.

## Extended summary

The paper formulates personalized presentation generation as a stateful, multi-turn authoring problem: given source material, a user profile, and an optional template, the system produces a "round-0" deck, then updates a session state and edits the deck in response to each subsequent user feedback turn. Three personalization signals with different lifetimes are distinguished: user profile memory (recurring cross-job preferences: theme, visual style, layout habits, content density), an optional task-time template (deck-local constraint for the current job), and session state (temporary, turn-specific requirements). When these conflict, explicit session feedback takes precedence, then template, then profile.

Multi-turn localized editing runs through a Plan-Act-Guard pipeline. Plan converts a revision request into an explicit "execution contract" (inferred scope, target slide paths, active rule identifiers, whether full coverage is required) rather than leaving scope implicit in the prompt. Act selects an editing tool matched to the contract (batch CSS update for a shared selector, semantic batch styling for common elements across structurally different slides, a layout-first local patch for single-slide content changes, or explicit page-level insert/delete; full-slide rewriting is reserved for new slides or corrupted-state recovery). Guard treats task completion as a checked state rather than a model decision: patches are bound to a content-hash snapshot of the target region (a stale snapshot triggers a rebinding hint rather than a blind overwrite), and premature finalization is blocked until required target coverage is verified. Working memory is the session-scoped layer connecting these three steps across turns, carrying active temporary preferences, carryover instructions, and edit-state records (resolved targets, coverage status, rebinding hints).

Long-term memory splits into two further modules. User profile memory stores intent-conditioned preferences (organized by theme, content, visual, layout, template, and general dimensions) per user and per intent; at job start, an intent-matched profile bucket is retrieved and reconciled against the current request (explicit conflicts override the stored preference for this deck; compatible items become active); at job end, only stable, transferable signals are consolidated back into long-term profile memory, filtering out transient one-off requests. Tool memory captures execution experience along two granularities: round-scope task experience (agent lessons, tool-error summaries, and auto-extracted patterns updated after each modify round) and finer-grained operation-scope tool-chain experience (segmented reasoning-tool-observation fragments retrieved before similar future tool calls).

Three evaluations are reported. (1) Persona-alignment judgments (Table 1): round-0 decks are generated for three personas across three backbone models (GPT-5, GLM-5, Gemini 3.1 Pro) and scored blind (judges see only the target persona summary and rendered deck images, not the prompt, parsed intent, or memory condition) on four 0-10 dimensions (Content, Structure, Visual, Specificity — Specificity uses distractor personas to check the deck doesn't read as generically "professional"). MemSlides wins all four dimensions against both DeepPresenter and SlideTailor on GLM-5 and Gemini 3.1 Pro, and wins 3 of 4 against each baseline on GPT-5. A supplementary 10-persona GPT-5 table (Appendix A.6) shows an average +2.42-point overall gain over DeepPresenter, with two personas (Legislator, Medical/health services manager) showing small negative deltas on at least one dimension. (2) A DeepPresenter-style general-quality check (Table 2: Constraint, Content, Style, Diversity) on the same decks finds MemSlides remains competitive (best average on GPT-5 and GLM-5) without a uniform sweep, checking that persona gains aren't bought at the cost of ordinary deck quality. (3) A diagnostic matched-pair tool-memory ablation (Table 3, Appendix Table 8-9): 9 fixed (source deck, model, persona, modify request) pairs are each run with and without tool-memory injection, measured on Closed-Loop Completion, Strict Verify After Change, Time to First Correct Edit, and Core Tool Time Ratio (excluding inspection/format-conversion calls). Overall, tool memory raises Closed-Loop Completion from 0.815 to 0.963, Strict Verify from 0.310 to 0.534, cuts Time to First Correct Edit from 609.5s to 242.5s, and reduces the geometric-mean Core Tool Time Ratio to 0.327x. A paired exact one-sided sign test (Appendix Table 9) finds Strict Verify and Core Tool Time Ratio statistically significant (p=0.0195 each, 8-1 win-loss), while Closed-Loop Completion (3-1, p=0.3125) and Time to First Correct Edit (6-2, p=0.1445) are reported as "directional" rather than significant.

Authors' stated limitations (Section 6, and echoed in Appendix A.11): evidence is scoped to controlled persona-alignment judgments, a diagnostic matched-pair modify setting, and qualitative working-memory cases; the profile bank and edit requests are proxies rather than a real-user deployment study; future work should add broader human studies, randomized edit sets, and memory consent/deletion/sensitive-preference safeguards. No new model training is performed (all reported experiments are inference-time agent evaluations via hosted APIs); no funding or acknowledgments section is present in the extracted text.

## Learnings

Separating agent memory by lifetime and function into three distinct stores — persistent cross-job user-profile memory (what the output should reflect), session-scoped working memory (temporary constraints active only for the current deck), and reusable tool/execution memory (how to execute an edit reliably) — rather than one undifferentiated context buffer is a specific, transferable architecture pattern for any personalization agent that must separately answer "what does this user want" and "how do I make this specific change without breaking something else." The paper's own tool-memory ablation supports that these serve genuinely different functions: it measurably improves execution reliability and efficiency metrics without being the mechanism responsible for the paper's separately-measured persona-alignment content gains.

The Plan-Act-Guard scoped-revision pattern — converting a natural-language edit request into an explicit execution contract (inferred scope, target paths, required coverage) before acting, and gating task completion behind an explicit coverage check rather than trusting the model's own decision to stop — is a specific, reusable technique for any agent editing a structured, mutable artifact (documents, code, configuration) where the alternative failure mode is repeated full-regeneration competing with the deck's own existing, already-correct state for limited context.

The snapshot-hash-bound patch mechanism (a proposed edit is tied to a specific content hash of its target region; a stale snapshot triggers an explicit rebinding hint rather than a blind overwrite or silent failure) is a concrete, transferable safety mechanism directly analogous to optimistic concurrency control in software systems, applicable to any agent performing scoped edits against an artifact that may have changed since it was last read.

## Verification

The paper's tool-memory ablation (Table 3, Appendix Tables 8-9) is a genuinely well-controlled diagnostic: matched pairs fix source deck, model family, persona, and request while varying only memory injection; the persona-alignment judging protocol is blind (judges see only the target persona and rendered images, not the prompt, intent, or memory condition, guarding specifically against the judge simply recovering instructions that were explicitly stated in the prompt); and the paper reports a non-parametric paired significance check (an exact one-sided sign test) rather than only means, explicitly flagging which metrics reach significance (Strict Verify, Core Tool Time Ratio, both p=0.0195) and which do not (Closed-Loop Completion p=0.3125, First Correct Edit p=0.1445) — a level of statistical transparency not every paper at this scale provides. The clearest gap is in the headline personalization claim: Appendix A.2 describes a "memory-injected condition and its matched control" designed to isolate profile memory specifically, but no such internal MemSlides-with-versus-without-profile-memory table appears in the results reported in the main text or appendix — Table 1's persona-alignment comparison is instead a cross-system comparison between MemSlides and two architecturally different prior systems (DeepPresenter, SlideTailor). This means the paper's own described ablation methodology for isolating the profile-memory contribution specifically is not the evidence actually presented for the paper's central personalization claim.

## Field context

MemSlides positions itself against a direct lineage of presentation-generation agents it names and compares against (PPTAgent's coupling of generation with presentation-specific evaluation, DeepPresenter's environment-grounded reflection, SlideTailor's template/reference-conditioned personalization) and against the broader agent-memory literature (MemGPT, Generative Agents, A-MEM, Mem0, Memory OS), arguing its distinguishing contribution is treating personalization as an explicit, lifetime-differentiated memory design rather than an implicit byproduct of prompting or template conditioning. Within this corpus, [reviews/2606.13681.md](2606.13681.md) (EvoArena/EvoMem), reviewed earlier in this same batch, converges on a related design principle from a very different application domain: EvoMem's append-only, evidence-grounded patch history for evolving agent environments and MemSlides' snapshot-hash-bound local patches plus tool-chain experience fragments both reject "overwrite to a single latest state" in favor of traceable, scoped memory updates, independently arriving at the idea that reliable agent memory needs a recoverable history of what changed and why, not just a consolidated current state.

## Critical discussion

The paper's tool-memory contribution is well-supported by its own evidence: a genuinely controlled matched-pair design, blind judging where applicable, and transparent statistical reporting (including which metrics fail to reach significance) make the execution-reliability claim credible within its stated diagnostic scope. The hierarchical memory architecture itself is clearly motivated and the paper is candid about scope limits (Section 6 explicitly frames the evidence as controlled proxies rather than deployment evidence).

Two concerns limit how much weight the paper's headline personalization claim (Table 1) can bear. First, despite Appendix A.2 describing a memory-injected-versus-matched-control ablation intended to isolate profile memory specifically, the actual reported evidence for the persona-alignment gains is a comparison between MemSlides and two different, architecturally distinct baseline systems (DeepPresenter, SlideTailor) rather than a MemSlides-internal with/without-profile-memory result; this means the observed gains are confounded with every other design difference between MemSlides and the baselines (the localized-revision engine, prompt design, generation pipeline), not isolated to the profile-memory mechanism the paper's title and abstract center on. Second, the evaluation scale throughout is very small — 3 personas in the main persona-alignment table (10 in a supplementary appendix table), 9 diagnostic matched pairs for the tool-memory claim, and a 30-entry profile bank partly filled via a "seeded completion" step using a role-preference registry rather than solely from accumulated real interaction — all reasonable choices for a controlled diagnostic study, and the paper's own Limitations section says so directly, but they leave open how the reported gains would hold at larger scale, across more diverse personas, or under real multi-session user deployment.

What remains solidly supported after these caveats: the tool-memory mechanism produces a real, well-evidenced improvement in localized-edit execution reliability and efficiency (particularly post-edit verification behavior and reduced non-inspection tool time), backed by a matched-pair design and an honest statistical accounting of which specific metrics reach significance; and the three-way memory separation (profile/working/tool) is a clearly articulated, well-motivated architecture whose components are shown to serve genuinely distinct functions, even though the paper's own reported evidence does not isolate the profile-memory component's causal contribution to the headline persona-alignment numbers as cleanly as its methodology description promises.
