Citation: Liu, J., Zhao, X., Shang, X., and Shen, Z. Dive into Claude Code: The Design Space of Today's and Future AI Agent Systems. arXiv tech report arXiv:2604.14228, 2026.

## What this paper is about

Claude Code is a widely used agentic coding tool, but Anthropic publishes user-facing documentation for it without a detailed architectural description. This paper reverse-engineers that architecture directly from the tool's extracted TypeScript source code and asks a broader question through that specific case: what recurring design questions does any production AI coding agent have to answer (where should reasoning live relative to the surrounding code, what safety posture should be the default, how should a bounded context window be managed, how should work be delegated to sub-agents, how should sessions persist), and how does one real, heavily used system answer them? The authors trace Claude Code's answers to five underlying human values (human decision authority, safety/security/privacy, reliable execution, capability amplification, and contextual adaptability) through thirteen concrete design principles down to specific source files and functions, then sharpen the analysis by comparing Claude Code against two independent open-source agent systems (OpenClaw, a multi-channel personal-assistant gateway, and Hermes Agent, a single-process multi-surface assistant) built for different deployment contexts, to see which design questions are genuinely recurring across systems versus specific to one product's choices.

## Extended summary

The paper's central architectural finding is that Claude Code's core agent loop is a simple while-loop (queryLoop(), an async generator) that calls the model, dispatches any requested tool use through a permission system, executes approved actions, and repeats; the paper reports a community-sourced estimate that only about 1.6% of the roughly 512,000-line, ~1,884-file extracted codebase constitutes this kind of AI decision logic, with the remaining 98.4% being deterministic operational infrastructure. The paper organizes this infrastructure into a seven-component high-level structure (user, interfaces, agent loop, permission system, tools, state and persistence, execution environment) and a finer five-layer subsystem decomposition (surface, core, safety/action, state, backend), tracing a single running example ("fix the failing test in auth.test.ts") through each subsystem across Sections 4 to 9.

The permission and safety architecture (Section 5) is deny-first: deny rules always override allow rules regardless of specificity, unrecognized actions are escalated to the user rather than silently allowed, and up to seven permission modes span a graduated autonomy spectrum from plan (all plans need approval) to bypassPermissions (minimal prompting, with safety-critical checks still active). This design is explicitly motivated by a cited internal finding that users approve about 93% of permission prompts, which the paper interprets as evidence that habituated interactive approval cannot be relied on as a sole safety mechanism, requiring independent automated layers (a two-stage ML classifier, optional shell sandboxing, hook-based interception) that function regardless of user attentiveness. The extensibility architecture (Section 6) uses four distinct mechanisms — MCP servers, plugins, skills, and hooks — deliberately organized by how much of the bounded context window each consumes (zero for hooks by default, low for skill descriptions, medium for plugins, high for MCP tool schemas), so that cheap extension points can be used liberally while expensive ones are reserved for cases that need a genuinely new tool surface. Context management (Section 7) treats the context window itself as the binding resource constraint and applies a five-stage compaction pipeline (per-tool-result budget capping, lightweight history trimming, cache-aware microcompaction, a read-time "virtual projection" over history, and full model-generated summarization as a last resort) before every model call, alongside a four-level, plain-text CLAUDE.md instruction hierarchy chosen specifically for user inspectability and version-controllability over more flexible but opaque alternatives like embedding-based retrieval. Subagent delegation (Section 8) gives each spawned subagent an isolated context window and its own restricted tool pool, returning only a summary to the parent rather than the full sub-conversation, which the paper connects to an "isolated subagent boundaries" design principle. Session persistence (Section 9) uses mostly append-only JSONL transcripts specifically to preserve auditability, resumability, and forkability without ever modifying previously written history, at the deliberate cost of not restoring session-scoped permissions on resume or fork, which the paper reads as a safety-conservative choice to avoid carrying stale trust decisions into a changed session context.

The comparative analysis (Section 10) contrasts these choices against OpenClaw (a persistent multi-channel gateway daemon serving WhatsApp, Telegram, Slack, and similar surfaces) and Hermes Agent (a single long-lived process whose role is set by its entry point) across six dimensions. All three systems answer the same recurring design questions differently: Claude Code places its trust boundary between the model and the execution environment (per-action evaluation), OpenClaw places it at the gateway perimeter (identity and access control for a single trusted operator), and Hermes sits between the two (per-action approvals rendered across many different surfaces). Claude Code's agent loop is the architectural center of the whole system; OpenClaw's loop is one component embedded inside a larger gateway control plane; Hermes's loop is a structural peer to Claude Code's but implemented as a synchronous, thread-managed process rather than an async generator. The paper also documents that Hermes's own project documentation has, in at least two specific places, drifted from what its source code actually does (a stated three-mode approval taxonomy that doesn't match the code, and a stated default delegation depth that doesn't match the code) — caught only by reading source directly, which the paper treats as validating its own preference for code-level over documentation-level evidence.

Section 12's discussion argues the architecture reflects a coherent philosophy of investing in deterministic operational infrastructure rather than explicit decision scaffolding (no hard-coded planning graphs, no rigid state machines), on the premise that a sufficiently capable model benefits more from a rich, well-instrumented environment than from constraints on its own reasoning — a philosophy the paper explicitly contrasts with graph-based orchestration frameworks like LangGraph. It documents specific value tensions the architecture creates (approval fatigue vs. protection; safety-layer performance costs vs. defense-in-depth; extensibility vs. attack surface) each backed by a cited piece of evidence, including a documented case where a shared performance constraint (per-subcommand parsing causing UI freezes for shell commands with more than 50 subcommands) causes several nominally independent safety layers to silently degrade together, and a cited pair of CVEs exploiting a "pre-trust initialization" ordering gap where hooks and MCP server connections execute before the interactive trust dialog and therefore fall outside the deny-first evaluation pipeline entirely. It also surveys published, independently-generated evidence about downstream effects of architecturally similar AI coding tools (a 16-developer randomized controlled trial finding AI tools made developers slower despite a perceived speedup; a causal study of 807 repositories finding a 40.7% code-complexity increase after adopting a similar tool; an EEG study finding reduced neural connectivity in LLM users; a large-scale commit audit finding persistent technical debt) to generate specific, falsifiable predictions about what Claude Code's own bounded-context, subagent-isolated architecture should produce, while being explicit that these studies target adjacent tools rather than Claude Code itself. Section 13 closes with six open questions (the observability-evaluation gap, cross-session memory persistence, where/when/what/with-whom the harness boundary will move, long-horizon "beyond a single session" reliability, governance and external regulatory constraints, and long-term developer capability), each grounded in specific external literature rather than left as unstructured speculation, and the paper's Conclusion frames the sustainability question (whether short-term capability amplification comes at the cost of long-term human understanding and codebase coherence) as the most consequential open design problem the architecture does not yet address.

## Learnings

An explicit "evidence tiering" scheme — separating claims drawn from official product documentation, claims directly traced to specific source files and functions (described here as the strongest tier), and claims reconstructed from community analysis or cross-system inference (explicitly stated with hedging language) — is a transferable discipline for any analysis mixing primary and secondary sources of uneven reliability, letting a reader see at a glance which specific claims rest on the strongest ground rather than presenting a uniformly confident narrative.

Comparing one system's answers to a set of recurring design questions against two architecturally independent systems built for different deployment contexts is what actually lets an analysis distinguish "a genuinely recurring, load-bearing question every such system must answer" from "an implementation detail specific to one product" — a single-system deep dive, however thorough, cannot make that distinction on its own, since it has no baseline for which of its observations reflect the domain and which reflect one team's particular choices.

A layered "defense in depth" safety architecture's real strength is not the number of independent-seeming layers but whether those layers actually fail independently; this paper's own documented example (a shell command with more than 50 subcommands falling back to one generic approval prompt because per-subcommand parsing caused UI freezes, silently disabling several nominally separate safety checks under a shared performance constraint) is a concrete illustration of how an "independence assumption" behind defense-in-depth can be violated in practice — a reusable diagnostic question for any layered safety or verification system: what constraint, if any, is actually shared across layers meant to be independent?

## Verification

This paper's own subject matter and its own method are the same kind of activity (analyzing what a system actually does versus what it claims to do), which makes its verification practices unusually visible and worth engaging with directly. The evidence-tiering system (Tier A: official documentation and creator statements, which "establish product intent but may not reflect internal implementation"; Tier B: claims citing specific files and functions in the extracted source, "the strongest evidence tier"; Tier C: community analysis, structural comparison, or inference, "stated with hedging language") is a genuinely disciplined self-verification practice, and the appendix states the evidence base concretely (roughly 1,884 files, about 512K lines of extracted TypeScript) alongside explicit limits of reverse-engineering as a method: source code reveals structure and control flow but cannot confirm design intent, which feature flags are actually enabled in production, how frequently a given code path actually runs, or unshipped behavior. The comparative analysis of Hermes Agent puts this preference for code over documentation into practice concretely, catching and reporting two specific places where that project's stated documentation contradicts its own source code. Where the paper's verification practice is less consistent with its own stated standard: the single most repeated and rhetorically load-bearing statistic in the paper (that only 1.6% of the codebase is AI decision logic versus 98.4% operational harness, used in the abstract and as the numerical anchor for the central "harness over scaffolding" thesis in Section 12.1) is explicitly sourced to community analysis, which by the paper's own scheme is Tier C evidence to be stated with hedging, yet it is presented and reused with a confidence that a reader could easily mistake for the paper's own Tier B code-verified measurement rather than an externally-sourced estimate the paper itself classifies as its weakest evidence tier.

## Field context

The paper positions itself explicitly within the software-architecture case-study tradition, applying that methodology, by its own framing, to a production LLM-based coding agent for the first time rather than to a traditional software system. It organizes the broader coding-tool landscape into a four-tier taxonomy by degree of autonomous action (inline completion tools like GitHub Copilot; chat-integrated IDE products like Cursor and Windsurf; agentic CLI tools like Claude Code, Codex CLI, and Aider; fully autonomous systems like Devin, SWE-Agent, and OpenHands), and grounds specific architectural choices in established agent-design literature (the ReAct pattern for the core reasoning-and-acting loop; Toolformer for learned tool use; existing surveys decomposing agents into planning, memory, and tool-use components). Its most distinctive methodological contribution beyond the single-system deep dive is the three-way comparative architecture analysis against OpenClaw and Hermes Agent, explicitly designed to separate structurally recurring design questions from product-specific answers, a form of controlled contrast that most prior single-system agent case studies do not attempt. It also connects its architectural analysis to a substantial and growing empirical literature on the downstream effects of AI-assisted coding (a 16-developer randomized controlled trial; a causal study of 807 repositories; an EEG study of cognitive effects; a large-scale commit-history technical-debt audit), using that external evidence to generate falsifiable predictions about what the documented architecture should produce, rather than resting the analysis purely on architectural description. None of these specific precedents (SWE-Agent, OpenHands, LangGraph, AutoGen, the cited RCTs and causal studies) are yet reviewed in this corpus, and this is the first paper in the corpus specifically about agent-harness/software-architecture design, as distinct from LLM reasoning capability or evaluation-methodology papers reviewed so far.

## Critical discussion

The paper's strongest evidence tier rests entirely on analysis of de-minified proprietary TypeScript source code extracted from a published npm package, not source code Anthropic has released for architectural inspection. The paper includes an explicit disclaimer that it used only publicly obtainable materials, does not intend to infringe intellectual property, and attributes the underlying rights to Anthropic, which is a reasonable and transparent framing of the method's legal posture. What the paper does not discuss directly is the broader research-ethics or responsible-disclosure question around publishing a detailed architectural map of a commercial system's internals (specific file paths, internal function names, feature-flag names) alongside a previously-reported network-security vulnerability's technical mechanism (a parser-differential gap in host-allowlist matching, described in a footnote), beyond citing the outside security researchers who originally found and reported it. This is worth naming plainly as an unaddressed methodological question, separate from whether the specific disclosure choices made here were themselves reasonable.

The analysis is explicitly and repeatedly self-described as a static snapshot of one specific version (v2.1.88), and the paper's own text documents at least one concrete case where the underlying system materially changed after that snapshot (a later version introducing "dynamic workflows" that relocate orchestration logic into a background script outside the model's context window entirely, discussed as a Tier A development the source-level analysis could not have anticipated). Given how frequently this specific product appears to ship changes (the paper itself required a v2 revision roughly three months after v1), many of its most specific numeric claims (54 built-in tools, seven permission modes, 27 hook events) should be read as accurate as of a particular date rather than as durable architectural facts, a limitation the paper states clearly in its own appendix but that bears repeating given how much of the paper's rhetorical precision rests on exactly these numbers.

The paper's most quoted statistic — that only 1.6% of the codebase is AI decision logic versus 98.4% operational harness — is explicitly sourced to community analysis rather than the paper's own Tier B code-verified measurement, making it Tier C by the paper's own scheme, yet it carries outsized narrative weight, appearing in the abstract and functioning as the numerical anchor for the paper's central interpretive thesis that Claude Code invests in harness over scaffolding. The paper's transparency about the statistic's origin is a genuine strength, but the gap between how confidently the number is used and how the paper's own methodology classifies its reliability is worth naming directly.

Finally, the paper's central interpretive move — tracing thirteen design principles back to five stated human values, and further tracing dozens of granular implementation choices (non-restoration of permissions on resume, subagent summary-only returns, the specific ordering of the five compaction layers) back to those principles — is fluent and internally consistent, but for many of the most granular claims this is necessarily an interpretive act rather than a directly-evidenced one: reverse-engineered code can establish what a system does, not with certainty why it was built that way. The paper's appendix states this limitation plainly at the level of the method as a whole, but the main text does not consistently flag, at the point of each specific value-to-implementation attribution, which links are directly evidenced (Tier A creator statements) versus the paper's own plausible reconstruction.

## Relevance to us

This is a directly relevant, unusually detailed case study for our own interest in agent orchestration and harness design (Tension 2, complex vs. deliberately simple agents), grounded in source code rather than marketing material for one of the field's most widely used coding agents. The "minimal scaffolding, maximal operational harness" principle documented here — investing engineering effort in deterministic infrastructure (context management, permission enforcement, recovery) rather than explicit planning graphs, on the premise that a sufficiently capable model benefits more from a rich, well-instrumented environment than from constraints on its own reasoning — is a concrete, evidenced instance of the "deliberately simple agents" side of our own tension, worth weighing directly against more heavily-scaffolded alternatives the next time we design an agent loop of our own. The defense-in-depth failure mode this paper documents (independent-seeming safety layers silently degrading together because they share an unstated performance constraint) is a specific, reusable caution for any layered verification or safety system we build ourselves: the paper's own diagnostic question — what constraint, if any, is actually shared across layers meant to be independent — applies directly whenever we stack multiple checks (a fast heuristic filter, a slower verifier, a human-in-the-loop step) and want to know whether they truly fail independently or share a hidden common cause. The paper's evidence-tiering methodology is itself a directly reusable practice for any of our own analyses that mix primary evidence with secondary or inferred claims, independent of the specific subject it was applied to here.
