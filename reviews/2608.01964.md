Citation: Ma, Z., Huang, H., Zou, S., Wang, Y., Yang, S., Hu, Y., Wei, F., Chu, X. LongHorizon-Harness: Advancing Long-Horizon Agents for Real-World Tasks. arXiv preprint, 2026. https://arxiv.org/abs/2608.01964v1

## What this paper is about

Most agent harnesses run a long-horizon task inside a single, continuously growing context: the same session both does the work and judges whether the work is done, so an incorrect self-assessment (the agent believing a stalled GUI dialog eventually worked, or that a visually plausible edit satisfies a stricter requirement) gets baked into the agent's own working memory and misleads every subsequent decision. This Alibaba paper reframes long-horizon execution as a task-state management problem rather than a single-trajectory problem: an explicit, external record of what has actually been verified is maintained outside execution, updated only by evidence a separate, read-only auditor independently confirms from the environment, with each executor working in a disposable fresh context that is discarded once a subtask is done.

## Extended summary

The core design is a Manage-Execute-Audit (MEA) loop with three roles that never share raw context with each other. A manager holds the persistent task state (structured records of requirements, produced artifacts, and discovered facts, each tagged completed/pending/blocked/untrusted) and has no direct access to the environment at all; it can only act on what auditors have verified. Given the current state, the manager selects one unresolved objective and issues a bounded "subtask contract" specifying the goal, acceptance criteria, and boundary constraints. A fresh-context executor (a GUI or CLI agent, instantiated through a thin AgentAdapter interface around an existing backend such as Claude Code, Codex CLI, OpenClaw, or Hermes Agent) receives only this contract plus the state records and audit reports the contract references, performs the subtask using its own native planning/tool-use loop within a time budget, and returns a summary; critically, this summary is explicitly treated as an unverified claim, and the executor's raw interaction trajectory and reasoning are discarded once the round ends. A separate auditor, restricted to read-only tools, independently inspects the resulting environment (not the executor's account of it) against the same acceptance criteria, and produces a report classifying completion status (complete/incomplete/blocked) and an integrity status (clean/suspect/violation, flagging any state-changing action it detects during its own supposedly non-mutating inspection). Only this audit report, not the executor's claim, can advance a task-state record to "completed," and only the accumulated task state and audit history persist across rounds; the loop terminates when the audited state satisfies the task, no permitted action can make further progress, user input is needed, or a round budget (25 rounds in the experiments) is exhausted.

The evaluation spans three benchmarks chosen to probe different long-horizon regimes: WeaveBench (114 tasks requiring coordinated GUI-and-CLI workflows across eight domains), OSWorld 2.0 (108 desktop-workflow tasks with a median human completion time around 1.6 hours), and Terminal-Bench 2.1 (command-line-only tasks with no GUI or visual component at all). Under a matched comparison (same backbone model, same Claude Code executor backend, differing only in whether LongHorizon-Harness's state-management layer wraps it), LongHorizon-Harness raises Qwen 3.7-Plus's WeaveBench PassRate from 51.8% to 80.7% (mean task score 0.702 to 0.835) and Terminal-Bench 2.1 success from 69.7% to 77.2%, and raises OSWorld 2.0 binary task completion from 2.8% to 8.3% (partial score 21.5% to 35.2%). On a 34-task OSWorld 2.0 subset with Claude Opus 4.7 as the backbone instead, binary completion rises from 20.6% to 35.3%, showing the gain is not specific to a weaker model being propped up; the paper explicitly frames this as evidence that model capability and harness design are complementary rather than substitutable ("stronger models and explicit task-state management therefore provide complementary gains"). A separate WeaveBench sub-table (17 "Games" tasks, comparing Claude Code with and without the harness on both Qwen 3.7-Plus and Claude Opus 4.7) makes a pointed, concrete illustration of this thesis: Qwen 3.7-Plus wrapped in LongHorizon-Harness reaches a mean score of 0.733, exceeding the 0.680 that Claude Opus 4.7 achieves with the unwrapped baseline harness, i.e., a smaller/weaker model plus better task-state management outperforms a stronger model without it on this specific slice.

The paper reports a per-role token breakdown showing the manager itself is cheap (2.0-8.1% of total tokens across the three benchmarks) while independent auditing is the main added cost (19.4-38.1% of tokens), and that the framework's overall overhead is highly task-dependent rather than a fixed multiplier: it costs roughly 2.3x baseline tokens on WeaveBench and 3.6x output tokens on OSWorld 2.0, but actually costs 24% fewer tokens than the baseline on Terminal-Bench 2.1 while still improving the success rate, because a capable model needs fewer audit-and-replan rounds to satisfy a contract. A breakdown by task type finds the largest gains concentrate on tasks requiring an agent to preserve, inspect, and revise state across an extended trajectory (Design and Spatial/3D domains on WeaveBench improve by 50-60 points; system-administration and game categories improve substantially on Terminal-Bench), while tasks bottlenecked by a single model capability (visual perception, math, coding, algorithm design) show smaller gains or occasional regressions, since independent auditing can catch and trigger recovery from an incorrect result but cannot supply a capability the underlying model lacks.

Four paired case studies (same task, same Qwen 3.7-Plus backbone, baseline versus LongHorizon-Harness) illustrate the specific mechanisms behind the aggregate numbers. In one, the baseline recognizes a Wireshark dialog is unresponsive but this observation stays embedded in its growing session, so it retries the same failed interaction for over 400 steps and exhausts its budget (score 0.59); the harness instead externalizes the failed interaction and unresolved evidence gaps into the task state, letting a later fresh-context executor focus directly on the missing evidence (score 0.92). In another, the baseline edits a document's XML directly, produces a visually plausible result, and terminates, but the task specifically requires the change be made through a particular application workflow, so it scores 0.00; the harness's auditor independently re-parses the document's underlying XML to confirm the required style was actually applied through the correct mechanism (score 0.89), illustrating the paper's central point that a plausible-looking executor claim is not treated as ground truth. A third case shows the harness preserving a "before" evidence requirement as an explicit pending record so a later executor completes it before an irreversible repair step, avoiding an inconsistent before/after record the baseline produces by repairing first and only partially capturing evidence afterward. A fourth shows the harness carrying a genuinely completed sub-result (a page-load optimization) forward in the task state so that later, separate executors can focus purely on the remaining evidence-collection requirements rather than needing to reconstruct or re-verify already-finished work within an ever-growing session that eventually runs out of budget on an unrelated stuck interaction.

The WeaveBench comparison against externally-reported baselines carries an explicitly disclosed methodological caveat: the paper's own runs use root privileges inside the benchmark's task virtual machine, while the officially reported baseline numbers (including the 41.2% PassRate the abstract's more dramatic framing compares against) use a regular user account, so the paper states these external numbers are included "as reference points rather than matched comparisons," basing its actual conclusion instead on the privilege-matched comparison against the same Claude Code harness (51.8% to 80.7%). Similarly, the Terminal-Bench 2.1 result using Codex as the executor backend with a different model (GPT-5.6 Luna, reaching 83.1%) is reported without an equivalent unwrapped baseline for that exact same model-and-harness combination, so that specific number is not part of a matched ablation the way the Qwen 3.7-Plus results are.

## Learnings

The specific architectural principle of never letting an executor's own self-report directly promote a task-state record to "completed," requiring instead an independent, read-only auditor to confirm the claim against the environment before the state advances, is a directly transferable design pattern for any long-horizon or multi-step agent system where self-assessment errors are a concern: the mechanism generalizes beyond computer-use specifically, since the paper's own Terminal-Bench 2.1 result (a pure command-line domain with no GUI or visual perception involved) shows the same pattern of gains, indicating the benefit comes from decoupling execution from verification rather than from any GUI-specific mechanism.

The finding that a harness's token overhead is not a fixed multiplier but depends on how many audit-and-recovery rounds the underlying model actually needs (with the same framework costing more tokens than baseline on two benchmarks but fewer on a third, precisely because a capable executor satisfies contracts in fewer rounds) is a useful, generalizable point for evaluating any agent-reliability intervention: a wrapper's cost-effectiveness should be measured relative to the specific model driving it, not assumed to be a constant overhead ratio applicable across all model-task pairings.

The specific finding that discarding an executor's raw interaction trajectory and reasoning after each round, while retaining only the auditor's verified summary, allows an agent to recover from a stalled or degenerate sub-interaction that would otherwise consume the entire remaining budget (the Wireshark dialog case, where a baseline spends 400+ steps stuck on the same unresponsive UI element within one growing session) is a specific, transferable insight about a failure mode of long-context, single-session agent designs: a failure that is "noticed" by the agent in its own reasoning but never externalized into a structured, actionable record can still trap the agent indefinitely, because noticing a problem in free-text reasoning is not the same as encoding it as a fact the next planning step is forced to act on.

## Verification

The paper's central causal claim (that explicit task-state management, not merely a different model or a different amount of compute, drives the reported gains) is supported by a specific, controlled design choice: the matched comparisons hold the backbone model and the underlying execution backend (Claude Code) fixed and vary only whether the MEA state-management layer wraps it, which isolates the layer's contribution from confounding differences in model capability or executor implementation. This is reinforced by testing two backbone models (Qwen 3.7-Plus and Claude Opus 4.7) and finding consistent directional gains for both, arguing against the harness merely compensating for a weak model, and by the Terminal-Bench 2.1 result specifically, which the paper uses to argue the mechanism is not GUI-specific since that benchmark involves no visual interface at all. The per-role token analysis and the task-type breakdown are both genuine attempts to explain the mechanism behind the aggregate numbers (where the cost goes, and which kinds of tasks benefit) rather than reporting only a single top-line improvement figure, and the four paired case studies with detailed trajectory excerpts give concrete, inspectable evidence for the specific failure modes the framework is claimed to fix, rather than asserting the mechanism without an example.

Two verification gaps are worth naming. First, the paper's own text discloses that its WeaveBench comparisons against most external baselines use a different privilege setting (root versus regular user) than the officially reported numbers, explicitly calling those external comparisons reference points rather than matched baselines; the abstract's framing ("nearly doubling the strongest officially reported result of 41.2%") foregrounds this less rigorous comparison ahead of the paper's own, more careful, privilege-matched comparison (51.8% to 80.7%), which is the number the paper's body text says the actual conclusion rests on. Second, most of the reported benchmark numbers appear to reflect single runs per configuration (with the exception of Terminal-Bench 2.1, which the paper states is averaged over three independent runs per task), so the WeaveBench and OSWorld 2.0 results, including some fairly granular per-domain and per-task breakdowns in Table 4 and Fig. 6, cannot be distinguished from ordinary run-to-run variance using the evidence presented, which matters given how detailed some of the sub-benchmark claims are (e.g., specific per-domain point gains).

## Field context

The paper explicitly builds on and modifies existing agent harnesses (Claude Code, Codex CLI, OpenClaw, Hermes Agent) rather than proposing a new base agent loop, using its AgentAdapter interface to wrap their native planning-and-tool-use loops as interchangeable executor backends while adding the surrounding manage/audit structure; it also cites and positions itself against a broader "long-horizon agents" survey and against the METR finding that agent task-completion horizons are doubling roughly every four to seven months, arguing (consistent with a cited concurrent paper) that a longer horizon does not by itself make execution reliable. Within this corpus, two connections are directly relevant. [reviews/2604.14228.md](2604.14228.md) (Dive into Claude Code) reverse-engineers the internal architecture of exactly the same three harnesses (Claude Code, OpenClaw, Hermes Agent) that LongHorizon-Harness treats as interchangeable executor backends, tracing their existing context-management and sub-agent-delegation design choices from source code; reading the two together, LongHorizon-Harness's fresh-context-executor-plus-external-audit pattern can be understood as an additional architectural layer imposed on top of whichever context-management strategy each underlying harness already implements internally, rather than a replacement for it. [reviews/2605.26302.md](2605.26302.md) (Your Agents Are Aging Too) independently diagnoses a closely related but distinct problem, that a deployed agent's effective reliability degrades across many sessions even with frozen model weights, due to mechanisms like context compression, memory interference, and fact revision, and proposes a benchmark that isolates which specific stage of an agent's memory pipeline is responsible for a given degradation; LongHorizon-Harness's task-state externalization and independent auditing address a related but narrower problem (self-assessment errors compounding within a single long task) using an architecturally similar remedy (moving verified state outside the growing execution context), and the two papers together suggest that externalizing and independently verifying an agent's working state, whether across a single long task or across many sessions over an agent's deployed lifetime, is a recurring architectural response to a recurring class of long-horizon reliability failures.

## Critical discussion

The paper's matched-comparison design (same model, same executor backend, varying only the state-management layer) is a real methodological strength that isolates the contribution of the proposed architecture from confounds like model capability or backend implementation differences, and testing across three benchmarks spanning hybrid GUI/CLI, pure desktop, and pure command-line domains, plus two backbone models, is a genuine breadth-of-evidence effort beyond a single benchmark or model. The detailed case studies with concrete, quoted trajectory excerpts are a specific, checkable form of mechanistic evidence rather than an unillustrated claim, and the paper's honest reporting of task-dependent cost (sometimes cheaper, sometimes several times more expensive than baseline) and of tasks where the framework provides little or no benefit (single-capability-bottlenecked tasks) both count in its favor as candid, non-cherry-picked reporting.

Two points temper the strongest version of the paper's claims. First, the abstract's headline framing leans on the WeaveBench comparison against externally reported baselines run under a different privilege setting, which the paper's own body text explicitly says should be read as a reference point rather than a matched comparison; a reader should anchor on the paper's own privilege-matched, same-harness comparison (51.8% to 80.7%) as the more rigorously supported number, and treat the "nearly doubling the strongest officially reported result" framing as a looser, less controlled comparison layered on top of that stronger evidence. Second, most reported results appear to be single-run point estimates (Terminal-Bench 2.1 being the disclosed exception with three runs per task), so the more granular sub-benchmark claims (specific per-domain point gains in Fig. 6, or the individual per-task scores in Table 4) should be read as descriptive of these particular runs rather than as statistically established differences, a limitation the paper does not itself flag but which is a standard concern for any single-run agent-benchmark comparison, especially given how large the reported absolute margins already are for the WeaveBench and Terminal-Bench 2.1 headline results specifically.

What remains well supported after these caveats: the core mechanism, that decoupling task-state advancement from an executor's own self-report and gating it instead behind independent, read-only environmental verification, produces consistent, matched-comparison gains across three structurally different task domains and two backbone models, is demonstrated with both aggregate numbers and concrete, mechanistically-specific case studies rather than resting on either alone; the finding that the framework's benefit concentrates specifically on tasks requiring sustained, multi-step state preservation and revision rather than tasks bottlenecked by a single model capability is a well-targeted and non-trivial diagnostic result, precisely because it is not a uniform "improves everything" claim; and the Terminal-Bench 2.1 result specifically supports the paper's claim that the mechanism generalizes beyond GUI/computer-use settings, since that benchmark involves no visual or GUI component for the framework's audit-and-recovery loop to exploit.
