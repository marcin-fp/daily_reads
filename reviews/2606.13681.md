## What this paper is about

Most agent benchmarks test a model on one fixed, unchanging environment snapshot, but real deployments keep changing: APIs get updated, codebases evolve, and user preferences shift over time. This paper introduces EvoArena, a benchmark that turns three existing agent benchmarks (terminal tasks, software repositories, and personalized conversation) into chains of progressively evolving versions of the same underlying task, so an agent's ability to track what changed and what still applies becomes directly measurable. It also proposes EvoMem, a lightweight memory design that keeps a git-like history of memory updates (not just the latest state) so an agent can look back at why something changed when that matters, and shows this consistently helps, especially at the harder "solve the whole evolving chain, not just one version" level.

## Extended summary

EvoArena has three subsets, each built by extending a static benchmark into a version chain rather than by generating new content from scratch. Terminal-Bench-Evo (from Terminal-Bench) converts 89 initial tasks into 5-stage version chains (356 constructed, 352 after quality control, 441 total instances including originals) via a five-stage pipeline: extract a structured "workflow state" (objective, environment, files, dependencies, interfaces, validation rules) from each original task; design an evolution plan drawn from a taxonomy of I/O/protocol, CLI/API, dependency/toolchain, workspace/module, and semantic/policy changes; realize each version so that it inherits the prior version's already-realized environment (later changes persist unless explicitly revised); and run quality control plus oracle-solution validation to ensure every version is independently executable and solvable. SWE-Chain-Evo (from real GitHub repositories, not SWE-bench directly) builds 50 evolution chains across 12 repositories (493 chain-step instances, 145 unique milestones, 5-15 steps per chain) by grouping chronological commits into coherent SWE-bench-style milestones, then advancing the repository state after each evaluated step using the reference patch (not the agent's own predicted patch) — a deliberate design isolating "can the agent adapt to an evolving codebase" from "does the agent's own earlier error compound." PersonaMem-Evo (built on PersonaMem-v2) instantiates ordered preference trajectories for 10 personas (505 multiple-choice questions total) via long, mixed-topic conversation histories (median 597 turns, 174.7K tokens) where earlier stated preferences remain in context as the user's preference evolves, with dual-blind filtering removing any question answerable from persona stereotypes or interaction-free priors alone. All three subsets report both step accuracy (per-version-task correctness) and chain accuracy (a chain counts only if solved end-to-end, or for SWE-Chain-Evo, the fraction of consecutively-solved milestones from the chain start).

EvoMem augments an existing agent memory system with an append-only patch log rather than replacing it: for each non-additive memory update (a revision or overwrite, not a purely additive new fact), it records the pre- and post-update content, the update rationale, a semantic change summary, and the supporting evidence that triggered the change. At inference time the agent retrieves from the latest consolidated memory as usual, plus separately retrieves the top-k relevant patches when a query depends on overwritten states or version-specific behavior, concatenating both into context. The paper instantiates this abstraction across four different agent memory formats — Terminus2 (distilled terminal strategy), OpenHands (distilled software-engineering context), A-Mem (semantically-linked notes), and Memento-Skill (a global tip file) — arguing the interface generalizes across memory representations.

Main results (Table 3-4): base agents (paired one-to-one with an agent scaffold per subset: Terminus2 for Terminal-Bench-Evo, OpenHands for SWE-Chain-Evo, A-Mem for PersonaMem-Evo, tested across 5-8 backbone LLMs) achieve only moderate step accuracy (43.6% average on Terminal-Bench-Evo, 29.2% on SWE-Chain-Evo, 46.5% on PersonaMem-Evo) and substantially lower chain accuracy (21.5%, 10.6%, 39.1% respectively) — the step-versus-chain gap is the paper's central descriptive finding, showing that solving individual versioned tasks does not reliably compose into solving an entire evolution chain. Adding EvoMem improves average step accuracy by 2.4/0.4/1.7 percentage points and chain accuracy by 6.1/2.1/3.2 points on the three subsets respectively (larger gains at the chain level throughout), and also improves two standard benchmarks tested for generality, GAIA (+6.5 average, LLM-judge accuracy) and LoCoMo (+3.3 average, exact match). The per-backbone breakdown (Table 3) is not uniformly positive: on SWE-Chain-Evo, Gemini-3.1-Pro (-2.4) and Kimi-K2.6 (-2.6) step accuracy regress under EvoMem even as chain accuracy for the same two backbones improves; on PersonaMem-Evo, GLM-5.1 regresses on both step (-2.9) and chain (-3.7) accuracy.

Mechanism analysis (Section 6) stratifies EvoMem's gains by whether its retrieved information is actually used. On Terminal-Bench-Evo, the accuracy gain over baseline rises from 2.6% (no patch-transition terms reused in later reasoning/commands) to 8.3% (patch uptake nonzero), supporting the claim that EvoMem helps specifically when the agent operationalizes retrieved transition information rather than just receiving more context. On SWE-Chain-Evo, EvoMem reduces the average Pass-to-Pass regression rate (previously-passing tests broken by the agent's current-milestone patch) from 9.09% to 6.32% across backbones, indicating it helps preserve behavior established by earlier milestones while implementing new requirements. On PersonaMem-Evo, EvoMem's gains concentrate on temporal-trajectory and multi-pattern-synthesis questions (+5.2 points each) — the categories requiring tracking a preference across time or combining dispersed evidence — while conflict-resolution and single-pattern-transfer questions see small decreases; a direct evidence-capture measurement shows EvoMem raises row-level capture (all clauses needed for a question retained together) from 72.5% to 74.9%, more than clause-level capture (89.4% to 90.3%), indicating the mechanism specifically helps preserve complete evidence sets rather than just more evidence fragments. A token-usage-versus-accuracy analysis (Fig. 8) finds no reliable relationship between larger inference budgets and higher accuracy across backbones on either PersonaMem-Evo or Terminal-Bench-Evo, with some models achieving strong accuracy at well-below-average token cost and others (e.g., MiniMax-M2.7 on Terminal-Bench-Evo) spending far above-average tokens for below-average accuracy. ## Learnings

The core benchmark-construction technique — taking a fixed static task, extracting its structured "state" (objective, environment, dependencies, interfaces, validation rules), generating a taxonomized evolution plan over that state, and materializing each new version so it inherits the prior version's already-realized changes, followed by independent oracle-solvability validation of every version — is a reusable recipe for converting essentially any static, executable benchmark into a "does the agent track drift" benchmark, not specific to terminal tasks. The inheritance-plus-oracle-validation combination is the specific mechanism that keeps this rigorous rather than merely relabeling unrelated task variants as a "chain."

The step-versus-chain accuracy gap, demonstrated across three structurally different domains (SWE-Chain-Evo: 29.2% step vs. 10.6% chain), is a transferable evaluation-design lesson for any benchmark with sequentially-dependent tasks: aggregate per-step accuracy systematically overstates real deployment reliability whenever a task requires sustained correctness across a chain of linked decisions, since even independent per-step error rates compound multiplicatively across a chain's length.

The "operationalization" diagnostic — checking not merely whether relevant memory was retrieved, but whether its content is measurably reused in the agent's subsequent reasoning or, more strictly, its executed actions — is a specific, transferable technique for distinguishing two different memory-augmented-agent failure modes that require different fixes: "the needed evidence wasn't retrieved" (a retrieval problem) versus "the needed evidence was retrieved but not used" (a reasoning/attention problem). The paper's own stratification (2.6% gain with no patch uptake vs. 8.3% with nonzero uptake) is a concrete quantification of how much this distinction matters.

## Verification

The paper's mechanism analysis (Section 6) is a genuine methodological strength: rather than stopping at an aggregate accuracy improvement, it stratifies EvoMem's gain by specific, independently-measurable conditions (patch retrieval, evolved-requirement coverage, patch uptake, command-level uptake on Terminal-Bench-Evo; Pass-to-Pass regression rate on SWE-Chain-Evo; clause- versus row-level evidence-capture on PersonaMem-Evo) to build a specific causal account of when and why the method helps, rather than treating the score bump as self-explanatory. This is more rigorous than a typical single-number ablation. Two gaps limit the results' generality. First, each EvoArena subset is evaluated with exactly one fixed agent scaffold (Terminus2, OpenHands, and A-Mem respectively), so no experiment distinguishes whether EvoMem's benefit is a general property of patch-based memory or specific to how well it happens to compose with these three particular scaffolds; no cross-scaffold swap is reported. Second, no repeated-run variance is reported anywhere in the main results, and several reported deltas are small (many under 3 percentage points) and inconsistent in sign across backbones within the same benchmark — for instance, on SWE-Chain-Evo, Gemini-3.1-Pro and Kimi-K2.6 both show a step-accuracy *regression* under EvoMem even as their chain accuracy improves — which the paper's summary language ("EvoMem consistently improves performance across all EvoArena subsets") does not fully carry forward, even though the underlying per-backbone numbers are transparently reported in Table 3.

## Field context

EvoArena positions itself (Table 1) against static agent benchmarks (WebArena, SWE-bench, GAIA, AgentBench, AndroidWorld, Terminal-Bench, WorkArena++, PersonaMem) that fix task distribution and success criteria once constructed, and against recent partially-dynamic benchmarks it argues test only one dimension of change — GAIA2's asynchronous events, SWE-bench-Live's task refresh, Benchmark Self-Evolving's generated task variants, and HorizonBench's single preference-update personalization — arguing none combine persistent versioned evolution of the same environment, implicit change detection, and chain-level evaluation together. Within this corpus, the closest connection is [reviews/2605.26302.md](2605.26302.md) ("Your Agents Are Aging Too: Agent Lifespan Engineering for Deployed Systems" / AgingBench): both papers independently argue that single-session, static evaluation systematically overstates a deployed agent's real-world reliability, and both trace the failure specifically to memory-update mechanics rather than to reasoning ability in general. AgingBench's "revision aging" mechanism (a changed or derived fact silently failing to update or propagate correctly through memory) is mechanistically close to EvoArena's "state collapse" failure mode (a memory update overwriting an earlier rule that remains valid for an older version, a different context, or a future rollback) — the two papers frame the same underlying problem from opposite directions: AgingBench treats it as the agent's own accumulating session history degrading under a frozen environment, while EvoArena treats it as the external environment itself changing across releases while the agent's memory fails to track which state applies when. Read together, they are complementary evidence that memory consolidation silently discarding version- or time-relevant context is a broadly reproducible failure mode across different benchmark designs, model families, and framings of "why is the environment/state changing."

## Critical discussion

The paper's central descriptive claim — that current strong agents perform substantially worse at completing an entire evolution chain than at solving individual versioned steps — is well supported and consistent across all three structurally distinct EvoArena subsets, and is a genuinely useful reframing of what "agent robustness" should mean beyond a single static task. EvoMem's mechanism analysis is a real strength: it does not merely report an aggregate improvement but ties specific gains to specific, independently verifiable behavioral conditions (patch uptake, regression-rate reduction, evidence-capture completeness), which is a more rigorous validation than most "add a memory module, report higher accuracy" papers in this space provide.

Three limitations temper the strength of the EvoMem comparison specifically (as distinct from the EvoArena benchmark's own descriptive contribution, which stands on its own). First, the main-text claim that EvoMem "consistently improves performance across all EvoArena subsets" is accurate only on average: the full per-backbone table shows real regressions (Gemini-3.1-Pro and Kimi-K2.6 step accuracy on SWE-Chain-Evo; GLM-5.1 on both metrics on PersonaMem-Evo), so a reader relying on the prose summary rather than Table 3 would not learn that EvoMem sometimes measurably hurts a specific backbone on a specific metric. Second, because each EvoArena subset pairs with exactly one fixed agent scaffold, the paper cannot separate a general benefit of patch-based memory from a benefit specific to how EvoMem happens to compose with Terminus2, OpenHands, and A-Mem individually; a cross-scaffold experiment (e.g., EvoMem inside OpenHands evaluated on Terminal-Bench-Evo) is not reported. Third, no run-to-run variance is reported despite several of the highlighted deltas being small and, as noted, occasionally sign-inconsistent within the same benchmark, making it hard to fully distinguish a reproducible mechanism from noise at the level of individual backbone-benchmark cells (the aggregate, cross-backbone trend is more robust than any single cell). Separately, SWE-Chain-Evo's oracle-state-progression protocol (advancing the repository with the reference patch rather than the agent's own predicted patch after each step) is an explicit, disclosed design choice that isolates adaptation-to-evolving-state from compounding-agent-error, but it also means the benchmark does not test the harder and arguably more realistic deployment condition where an agent must keep functioning correctly on top of its own accumulated prior mistakes.

What remains solidly supported after these caveats: current strong agents show a large, robust step-versus-chain accuracy gap under persistent environment evolution across three independently-constructed task domains, a finding that does not depend on EvoMem at all and stands as EvoArena's primary empirical contribution; and EvoMem's specific mechanism — recording non-additive memory updates as retrievable, evidence-grounded patches — produces a real, mechanistically-explained improvement on average across backbones and domains, even though its benefit is not uniform across every individual backbone-benchmark combination tested.
