Citation: George, R. J., Adkisson, W., and Anandkumar, A. FloatLib: Verified Floating-Point Arithmetic in Lean. arXiv preprint, 2026. https://arxiv.org/abs/2609.19352v1

## What this paper is about

When a program computes with floating-point numbers, a proof about the underlying real-valued formula says little about what the code actually returns: small terms get lost, values overflow, and where rounding happens changes the answer. Machine-learning workloads make this sharper because they mix many low-precision formats (FP8 variants, bfloat16, posits, block-scaled microscaling) with wider accumulators. The authors built FloatLib, a Lean 4 library that models many number formats (IEEE binary and decimal of any width, posits of any width, the draft IEEE P3109 machine-learning formats, and user-defined formats and rounding rules) and runs them through several fast software implementations, each of which carries a machine-checked proof that it returns exactly what a reference specification returns on every input. Separate theorems connect those specifications to real-number rounding, error bounds, and exactness. They benchmark it against MPFR, SoftFloat, Universal, and two other Lean libraries, and test the specifications against more than 102 million TestFloat cases with zero differences. The comparison against SoftPosit turned up rounding and exponent-packing bugs in SoftPosit's generic routines.

## Extended summary

Architecture. FloatLib has four layers: exact numerical representations (dyadics, signed rationals, rounding and quantization contracts), word and limb kernels (64- and 128-bit unsigned arithmetic, certified division, restoring square root), format models (stored bits, reference operations, status flags, real-valued theorems), and certified execution. Storage and meaning are separate type classes (`EncodedFormat`, `FormatSemantics`) that assume no radix or bit layout; a value denotes a finite scalar, an infinity, or an exceptional value. A quantization contract relates an exact input to an output in a context that may carry a rounding mode, a shared scale, or explicit random bits. A four-entry nonuniform codebook example shows a new representation reusing the library's nearest-entry quantizer, with a generic theorem that the chosen entry minimizes distance (ties go to the lower code).

Binary formats. A binary descriptor fixes exponent width ew ≥ 2, fraction width fw > 0, a bias, and an exceptional-encoding policy; binary32 is (8, 23) and a custom 24-bit layout (8, 15) with precision 16 uses the same definitions and theorems. Reference operations compute finite intermediates exactly and round once when packing; FMA rounds the exact xy + z once. Status-returning operations expose five IEEE flags as returned data, with tininess detected after rounding. A worked example in the custom format shows the rounding point matters: with a = 1 + 2^-9, x = 1 - 2^-9, b = -1, FMA returns -2^-18 while separate multiply-then-add returns 0. The real interpretation forgets the sign of zero and maps nonfinite values to zero, so real-valued theorems state finiteness explicitly.

Theorems about rounding. Following Flocq's radix-and-exponent formulation, rounding reduces to an integer decision on a scaled significand. Theorem 1: nearest-even rounding error is at most half an ulp, and at most 2^-P relative in the normal range. Theorem 2 (finite arithmetic bridge): for descriptors with IEEE conventions and conventional bias (the `isIEEE` predicate, which admits nonstandard widths), the real value of an encoded sum, difference, product, or FMA equals the real rounding of the exact result, provided operands and result are finite; the finiteness premise is essential because the grid rounder has no overflow. Division and square root have analogous statements; directed operations give outward enclosures in the extended reals. Theorem 3 is an encoded Sterbenz lemma: for positive finite u, v with u ≤ 2v and v ≤ 2u, subtraction is exact with no separate finiteness assumption; the authors note that flush-to-zero would invalidate it because cancellation can produce subnormals. A Lean example proves both the encoded equality and a one-rounding theorem for an affine operation ax + b in the custom 24-bit format without unfolding the selected backend.

Certified execution. Every backend is a `Certified` record pairing an implementation with a cost estimate and a proof `run = spec` covering every operand, including exceptional values. A planner folds over certified alternatives onto a mandatory certified baseline using estimated warm and cold costs under a user policy and memory ceilings; its output is still `Certified spec`, so correctness does not depend on the cost model being accurate. Memory ceilings are selection preferences, not proved resource bounds. Kernels have eligibility conditions (for example, the two-word binary kernel requires IEEE conventions, more than 64 fraction bits, and at most 128 encoded bits) and may decline an operand, in which case a dispatcher calls the reference implementation under the same equality theorem. For byte-sized formats, binary operations use exhaustive tables (2^16 input pairs), each entry proved equal to the reference; an eight-bit FMA table would need 2^24 entries, so FMA uses the exact baseline.

Guard, sticky, and division kernels. Long exact alignments are avoided by "shift right with jamming": J_j(x) is floor(x / 2^j), with the low bit set if any discarded bit was nonzero. Theorem 4: if j + 2 ≤ s, nearest-even rounding of the jammed value by s - j equals nearest-even rounding of x by s. The condition cannot be weakened in general (x = 5, j = 1, s = 2 gives a different answer), and the appendix gives a family of counterexamples for every j ≥ 1. The wide-limb subtraction kernel (32-bit limbs, IEEE-style descriptors wider than 128 bits, exponent fields of at most 32 bits) uses a cancellation guard to justify the compressed branch and proves the limb borrow is accounted for before jamming; wide-limb FMA forms an exact limb product and reuses the same theorem. Division separates proposal from acceptance: a radix-2^32 implementation of Knuth's Algorithm D proposes a quotient and remainder for 64 < p ≤ 126, a runtime check accepts only if qd + r = n·2^s and r < d (Theorem 5, soundness; the appendix also proves completeness and that the carry test excludes no representable pair), and a proved restoring divider handles rejection. One correctness theorem covers both branches; the check executes at runtime while its soundness proof is erased.

Parsing and native types. Configured binary types parse decimal, hexadecimal, dyadic, and special-value text through the descriptor model; bounded parses are proved equal to the unbounded parser, and fixed and scientific decimal output carry proved nearest-even error bounds on the value the printed string denotes. The released library targets Lean 4.34.0 and bridges binary32/64 to Lean's logical `Float32` and `Float` models for integer constructors, finite addition and subtraction, and square root, with NaN canonicalization accounted for. The authors state that these proofs are equations between Lean functions, including logical models of native operations; they do not verify machine instructions, and compiled execution relies on Lean's compiler and runtime. Proved `@[csimp]` equations substitute faster functions at compile time. Separate `NativeFPU.Unchecked` adapters use host arithmetic without the equality certificate; the benchmarked FloatLib paths use the proved software kernels.

Posits and elementary functions. Standard (2022) posit rounding uses thresholds from the format one bit wider, T_n(u) = D_{n+1}(2u + 1), which is not nearest-value rounding: for four-bit posits, x = 3/128 rounds to 1/16 even though 1/256 is closer. Theorem 6 proves that a comparator-driven bisection over codes returns the standard rounding Π_n(y) for any real y whose comparisons with rationals are supplied exactly. Square roots get exact comparisons via t ≤ √a iff t² ≤ a. Exponential and logarithm use rational enclosures refined until they separate from the threshold; termination needs only endpoint convergence (no nesting or rate), and equality with a rational threshold is excluded because exp q and log q are irrational for the relevant rational q (exp 0 and log 1 handled directly). Rational powers, roots, trigonometric, and hyperbolic functions have corresponding comparison proofs. The optional binary elementary-function kernels are deterministic approximations whose certificates do not establish correct rounding of the real function; only the rational exp/log enclosures carry proved containment. Theorem 7: a standard 16n-bit quire accumulates fewer than 2^31 non-NaR products exactly, for every ordering, with a bound uniform in n; conversion to a posit then rounds the exact dot product once. Exactly 2^31 same-sign maximal products reach overflow or the NaR word.

Other families. Low-precision binary formats reuse descriptors with different exceptional policies (E5M2 and bfloat16 with IEEE conventions; E4M3FN with NaNs but no infinity; FNUZ variants; MX FP4 and FP6 with neither). Directed bounds for all-finite encodings require the exact result to be in range and do not cover the FN and FNUZ policies. Decimal32/64/128 and parameterized decimal layouts retain the quantum exponent (1.50 and 1.5 are distinct) with BID and DPD encodings, and nearest-even and nearest-away error bounds of half a grid unit for non-overflowing results. P3109 follows working-group report 4.0.3 (dated 1 September 2026, unapproved) with independent source and destination descriptors; stochastic modes take random bits explicitly and are proved only to land on the grid, which the authors note does not imply unbiasedness. MX couples 32 lanes through a shared E8M0 scale; saturating conversion minimizes each lane's error at a selected scale, not globally over scales, and the MX dot product is defined as exact accumulation followed by one binary32 rounding. Fixed-point, logarithmic, codebook, and shared-scale representations use the generic interface.

Benchmark setup. Addition, subtraction, multiplication, division, square root, and FMA are timed at binary widths 4 to 4096 (E2M1, E2M2, E3M2, E3M3, E4M3 at 4 to 8 bits; IEEE interchange at 16 to 128; 19 exponent bits above) and posit widths 2 to 4096 with es = 2. Binary addition uses tables at 4 to 8 bits, word kernels at 16 to 64, a fixed-limb kernel at 128, and the exact baseline at 256 to 4096; the optional limb-array carrier was not measured. Each operation cycles through sixteen fixed tuples rounded before timing, with a result fingerprint selecting the next tuple. Timing includes fixture selection, arithmetic, representation handling, and result observation, and excludes construction, compilation, and proof checking. Runs use an Intel Xeon Platinum 8488C pinned to one logical CPU, nine fresh-process trials per cell, 256 warmup iterations, 448 cells and 4,032 observations. The paper reports medians with empirical 5th to 95th percentiles across trials, explicitly not confidence intervals; the ratio plot has no uncertainty bands. MPFR 4.2.0 is configured to match precision, exponent range, and gradual underflow; SoftFloat and native C cover binary32/64. Universal passed 71 of 78 fixture checks (the seven failures are square roots at widths 64 to 4096); all Universal square roots are excluded, leaving 65 posit comparisons. A Flocq 4.2.2 OCaml wrapper's 84 cells are excluded because unmatched exponent bounds and separately rounded fixture numerators and denominators change the dependent sequence; the authors stress this concerns the wrapper, not Flocq's theorems.

Performance results. All 84 binary medians exceed MPFR's. Binary32 addition takes 138.6 ns in FloatLib against 34.1 ns in MPFR and 22.9 ns in SoftFloat, and all six binary32 operations are slower than both references; at binary64, addition is 312.8 ns and division rises from 123.7 ns (binary32) to 1,447.3 ns. Against Universal, FloatLib has lower medians in 34 of 65 posit cases, including all five operations at 64 bits and all twenty cases at widths 512 to 4096; the 31 slower cases include all twenty at widths 5 to 8. Posit multiplication is 288.9 ns (FloatLib) versus 266.5 ns (Universal) at 32 bits, 305.1 versus 684.9 ns at 64 bits, and 7.25 versus 839.63 µs at 4096 bits, the source of the abstract's 116× figure. The authors state that fixed fixtures and selected paths do not characterize arbitrary cancellation, exponent gaps, exceptional inputs, or application performance, and that timings do not isolate the contribution of each optimization.

Lean library comparisons. On a Xeon Platinum 8275CL with paired, alternating-order trials, FloatLib has lower medians than FLoPS in nine of twelve P3109 cases (Binary4p2sf, Binary8p4se, Binary8p3se; nearest-even, nonsaturating); FLoPS is faster for four-bit addition, multiplication, and FMA; FLoPS division costs 1.32 to 1.46 times FloatLib's median (the abstract's 1.46× figure); eight-bit FMA differences are small, with overlapping percentile intervals for Binary8p3se. The libraries use different Lean toolchains, so ratios include compiler differences, and FloatLib uses exact rationals where FLoPS uses dyadics. The two agree bit-for-bit on 529,152 results (all ordered pairs for add, multiply, divide; all four-bit FMA triples; a structured slice of eight-bit FMA). For binary32 conversions to and from FP16, bfloat16, E4M3FN, and E5M2, TensorLib is 5.9 to 13.0 times faster (FloatLib encode 2,201 to 3,643 ns versus TensorLib 253 to 280 ns); timed inputs are all normal, and TensorLib uses specialized bit-field operations. Both match an independent nearest-even reference on 952,612 cases, apart from 2,964 E4M3FN NaN-sign differences on overflow; status flags and NaN payloads are not compared.

Conformance testing (Table 5). TestFloat: 102,454,320 evaluations with zero differences, checking non-NaN words and five flags (NaNs by quiet or signalling class), four rounding directions, tininess after rounding; binary80, nearest-away, round-to-odd, and tininess-before-rounding are excluded. The adapter calls the logical `Model.*WithStatus` operations, not every timed backend. FMA accounts for 98,131,968 cases (95.78 percent). MPFR 4.1.0: 400 primitive-rounding plus 672 exact-reduction checks, and 131,072 binary16 cases on two fixed-first-operand rows. IBM FPgen: 81,513 of 130,471 records admitted, zero differences. Z3 QF_FP: 27,492 comparisons (25,168 by bits, 2,324 NaNs by class). Decimal references: 13,980 comparisons with zero differences reported, but the artifact contains only summaries, not the raw vectors, runners, or tested source revision needed to replay them.

SoftPosit discrepancies. Against SoftPosit revision 17d5628185b3 (exhaustive at widths 2 to 8, sampled elsewhere), 32,893,800 evaluations produced 7,564 differences from seven distinct input tuples; 7,560 of those occurrences repeat three 32-bit inputs. Four distinct inputs involve FMA: at width 14 the exact result 64768 + 2^-48 lies just above the rounding threshold 64768 between adjacent words, so the odd upper word is correct, but SoftPosit's generic FMA overwrites its recorded sticky information at final rounding, turning a non-tie into a tie and choosing the even lower word. The other three concern generic 32-bit add, multiply, and divide, where exponent packing shifts by 28 - 29 = -1, undefined behavior in C/C++. SoftPosit's named p32 operations agree with FloatLib. Source probes confirm both diagnoses on these inputs; the authors explicitly do not claim a proved repair.

## Learnings

FloatLib's division kernel lets an unverified fast algorithm propose a quotient and remainder, accepts them only after a cheap exact check (qd + r = n·2^s and r < d), and falls back to a slow proved divider otherwise. The correctness proof needs only the checker's soundness and the fallback, never the proposer. This is a clean small-scale instance of "prove the check, not the generator," and it transfers to any setting where a fast untrusted proposer is gated by a cheap exact verifier.

The sticky-bit jamming theorem needs the jam to sit at least two bits below the rounding position, and the paper shows the condition is tight. SoftPosit's generic FMA fails precisely by losing sticky information before the final rounding, so a mature library violated the invariant the paper proves. The bug appeared on only a handful of distinct inputs among tens of millions of evaluations, which argues for differential testing against an exact specification rather than relying on random sampling alone.

The evidence splits into two layers that answer different questions. Proofs show each backend equals the encoded specification. External oracles (TestFloat, IBM FPgen, Z3, MPFR) show the specification matches the standard, and the TestFloat adapter calls the logical model, not the compiled kernels. Neither layer substitutes for the other, and compiled execution against Lean semantics is covered only by fixture checks and the smaller cross-library comparisons.

"Round to nearest" is format-specific. Standard posit rounding uses thresholds from the next wider format, so 3/128 rounds to 1/16 in four-bit posits although 1/256 is closer. Any numerical check or tolerance that assumes nearest-value rounding will misjudge such formats.

Deciding a correctly rounded result for exp or log at a rational threshold terminates using only convergent rational enclosures, because irrationality rules out exact equality (exp q for rational q ≠ 0, log q for rational q > 0, q ≠ 1). No convergence rate is needed. The same argument shows why equality cases (here exp 0 and log 1) must be decided separately.

## Verification

Verification is the subject of the paper. Two kinds of check are used, at different levels.

Machine-checked proofs in Lean 4. Each admitted backend carries a `run = spec` proof over all inputs, including signed zeros and exceptional encodings. The planner's output keeps that type, so selection is correct whatever the cost estimates say. Numerical theorems connect the specifications to real arithmetic: half-ulp and relative error, the finite arithmetic bridge, encoded Sterbenz, jamming, quotient-check soundness and completeness, posit threshold rounding, exact quire accumulation, and enclosure comparison. The authors scope the guarantees carefully. Proofs concern Lean functions and Lean's logical models of native floats, not machine instructions. Compiled execution trusts the Lean compiler and runtime. `NativeFPU.Unchecked` adapters are uncertified. Binary elementary-function kernels are not proved correctly rounded. Stochastic rounding is proved only to land on the grid, not to be unbiased. MX quantization is optimal per lane at a chosen scale, not globally. The text does not state the development's axiom footprint or whether the exhaustive table certificates are checked by kernel reduction or by compiled evaluation.

External conformance and differential testing, all with deterministic verdicts. TestFloat (102,454,320 cases, 95.78 percent FMA; certain rounding modes and tininess conventions excluded), MPFR, IBM FPgen, and Z3 QF_FP all report zero differences under stated comparison relations. NaNs are compared by class, and payloads and signs are ignored. Decimal checks exist only as summaries. The comparisons with FLoPS (529,152 results agree) and TensorLib (952,612 cases agree with an independent reference) run public operations. The SoftPosit comparison found seven distinct failing inputs, and the authors trace them to two specific C-level defects.

## Field context

The authors position FloatLib as a Lean 4 descendant of Flocq, the Coq library of Boldo and Melquiond (2011 onward). Flocq introduced the radix-and-exponent abstraction for representability and rounding, and since version 4.2.2 (February 2026) it also provides verified executable binary operators. FloatLib adopts that abstraction and adds representation and quantization interfaces with no radix assumption. The closest Lean neighbors are FloatSpec (Beneficial AI Foundation, 2026), which brings Flocq-style theory and IEEE models to Lean but whose rounded IEEE operators are noncomputable in the cited version, and FLoPS (Chang, Park, Lim, Nagarakatte; arXiv:2602.15965), which formalizes P3109 semantics under report 3.2.1 with executable refinement proofs and stochastic-rounding bias analyses that FloatLib explicitly does not replicate. TensorLib handles tensor dtypes in Lean but computes low-precision arithmetic by casting to native floats. Further afield are Primitive Floats and CoqInterval/ValidSDP in Coq (hardware binary64 through axioms, used inside proofs), expression- and program-level roundoff tools (Gappa, VCFloat2, Fluctuat), SymFPU for SMT bit-blasting, and DSLean for importing external proofs into Lean. The authors state that FloatLib supplies local arithmetic facts and does not perform whole-program roundoff analysis. Per the authors, what is new is breadth under one interface (IEEE binary and decimal, arbitrary-width posits, P3109, MX, and user formats) together with executable, cost-selected software backends that each carry an equality certificate, plus conformance evidence against the standard references.

Timing: the paper follows the 2026 P3109 interim report (4.0.3, September 2026) and Lean 4.34.0, and comes months after FLoPS and FloatSpec. It enters a line of Lean formal-verification work, at a time when LLM-driven Lean proving is also active; the authors cite DeepSeek-Prover-V2 and AlphaCode as motivation but run no LLM experiments.

Connections within this corpus (reviewer inference; FloatLib cites none of these). The essay reviewed in reviews/26daedsci.md, authored by Anima Anandkumar (also an author here), proposes Lean-style formal verification as a complement to physics-based modeling and names LeanDojo. FloatLib is a concrete, arithmetic-level piece of formal numerical infrastructure consistent with that direction, though it does not itself touch PDEs or physics. The Lean physics formalizations in reviews/2607.06379.md (Seiberg-Witten) and reviews/2603.15770.md (free Euclidean QFT) validate computable content against an external mpmath/numpy oracle outside Lean. The Seiberg-Witten review records the distinction "sampling bounds falsity; statement-level review bounds fitness for purpose." FloatLib's split between proofs (implementation equals specification) and external oracles (specification matches the standard) is the arithmetic analogue of that distinction, and its proved rational enclosures are the kind of primitive that could move part of such an oracle inside Lean. The paper does not attempt this. The FP8 hybrid-precision training described in reviews/2609.13356.md is the kind of practice whose scalar formats (E4M3FN, E5M2) FloatLib models; FloatLib verifies no training pipeline.

## Critical discussion

The core correctness claim is strong and well designed. Because the `Certified` record requires a `run = spec` proof and the planner returns a `Certified spec`, "every admitted backend is proved equal to the encoded specification" is a type-level fact rather than a testing result, and it holds independently of the cost model. The theorems in the text are stated with their premises (finiteness, IEEE conventions, the j + 2 ≤ s separation, the 2^31 product bound), several come with counterexamples showing the premise is needed, and the limits of the guarantee (no machine-instruction verification, compiler and runtime trusted, uncertified native adapters, approximate elementary kernels, grid membership but not unbiasedness for stochastic modes) are stated plainly rather than buried. That candor is worth crediting.

The trust statement is incomplete in one respect that matters for a paper whose headline is "fully verified." The text does not report which axioms the development depends on. It also does not say whether the exhaustive table certificates (2^16 entries per operation at eight bits) are discharged by kernel reduction or by compiled evaluation such as `native_decide`, which would add the compiler to the trusted base for those proofs. Nor does it confirm the absence of unfinished proofs or give proof size and checking time. The only proof snippets shown use `decide +kernel` and `decide`, which is suggestive but not a statement. All of this may well be in the repository, but a later reader of the paper cannot tell what the "verified" in the title rests on. The decimal family is weaker still: its conformance evidence is 13,980 comparisons reported only as summaries, without the vectors, runners, or tested revision needed to replay them (the authors disclose this).

The TestFloat number needs reading with care. The adapter calls the logical model operations, not the timed backends. So the 102 million zero-difference result validates the specification against Berkeley's reference, which is the right thing to test. It says nothing directly about compiled kernels, whose agreement with the specification rests on the proofs plus trust in the Lean compiler. About 96 percent of the count is FMA, leaving roughly 4.3 million TestFloat cases for all other operations combined. Nearest-away, round-to-odd, and tininess-before-rounding have no external conformance evidence in the reported set. Compiled execution is exercised end to end only by the fixture checks and the FLoPS, TensorLib, Universal, and SoftPosit comparisons. None of this undermines the result, but "102 million evaluations" is less uniform coverage than it sounds.

The performance claims are more selective in the abstract than in the body. "Up to 1.46× over FLoPS and 116× over Universal" are maxima. By the paper's own numbers, FloatLib is slower in all 84 binary comparisons against MPFR, in every binary32 operation against SoftFloat and MPFR (addition 138.6 versus 22.9 and 34.1 ns), in 31 of 65 posit cases against Universal (including every case at widths 5 to 8), in all TensorLib conversions (by 5.9 to 13 times), and in 3 of 12 P3109 cases against FLoPS. The abstract's "slower in some regimes such as binary arithmetic against MPFR" is accurate but soft: in the one family that has a mature arbitrary-precision reference, FloatLib is slower in every measurement. The 116× figure (7.25 versus 839.63 µs for 4096-bit posit multiplication) mainly shows that Universal's wide posit path is slow, since no MPFR-class posit reference exists to show whether FloatLib is efficient in absolute terms. The FLoPS margin is confounded by different Lean toolchains and representations, which the authors acknowledge, and the only clear margin there is division. The fair reading of "efficient certified execution" is: competitive with other certified Lean libraries, faster than Universal for wide posits, and several times slower than the C references for binary arithmetic.

The benchmark is narrow in ways the authors acknowledge, and those ways matter for the kernels' design goals. Each operation cycles through sixteen fixed tuples. The Lean comparisons use only normal, exactly representable inputs. Subnormals, exceptional values, deep cancellation, and large exponent gaps are unmeasured, yet these are exactly the cases the guard-and-sticky and cancellation-guard kernels exist to handle. All runs use one machine class pinned to one logical CPU, with no application workload such as a dot product, solver iteration, or quantized layer. The optional limb-array carrier was not timed.

A natural internal control is also missing. The authors note that the timings do not isolate the contribution of each optimization, and the text reports no comparison of an optimized path (table, word, or limb kernel) against the certified exact baseline at the same width on the same fixtures. The proofs therefore establish that guard-and-sticky summaries and quotient checking preserve results, but the paper does not quantify how much computation they save, or whether the planner's cost estimates pick the fastest eligible backend. Relatedly, the win tallies (34 of 65, 9 of 12) count median orderings without reference to the reported spread. Some of those orderings are small, for example 8 percent at 32-bit posit multiplication, and one eight-bit FMA comparison has overlapping percentile intervals. A reader should treat near-parity cases as ties.

The motivation reaches further than the demonstration. The introduction frames FloatLib as enabling verified machine-learning programs and LLM-generated numerical proofs, and cites proof-checking time in CoqInterval as a reason speed matters inside proofs. The paper demonstrates scalar contracts and two loop-level results (the exact quire accumulation theorem and the custom-format affine bound). It does not verify an end-to-end mixed-precision kernel or training step, runs no LLM experiment, and excludes proof checking and in-kernel evaluation cost from all timings. These are scope limits, not errors, but they leave the stated applications as prospects.

The SoftPosit findings are well grounded. For the width-14 FMA case the text gives the decoded operands, the exact sum, the adjacent words, and the threshold, and the arithmetic is internally consistent: the exact result exceeds the threshold, so rounding up is correct. The 32-bit diagnosis names a specific undefined negative shift. The authors report seven distinct inputs rather than leading with the 7,564 raw differences, note that SoftPosit's named p32 routines agree, and decline to claim a verified fix. This is a model of calibrated bug reporting.

What remains supported after these caveats is substantial. FloatLib is a broad, extensible Lean 4 floating-point library whose certified software backends are equal to complete encoded specifications by construction, modulo an axiom footprint the paper does not state. Its theorems cover rounding error, finite real bridges, Sterbenz exactness with gradual underflow, jamming, checked division, posit threshold rounding, exact quire accumulation, and enclosure-based comparison. Its binary specification agrees with TestFloat, IBM FPgen, Z3, and MPFR on the tested relations, and its P3109 results agree with an independently developed Lean library. Its speed is competitive among certified Lean libraries and well behind C references for binary formats. The novelty claim of first Lean library to unify these families is scoped "to our knowledge" and is consistent with the comparison in Table 1.

## Relevance to us

This is formal numerical infrastructure, not a physics verifier. Most of it sits outside what we build, and at the formal-proof end that experimental groups told us they did not ask for. Two points still bear on our verification programme.

First, the division kernel is a small, fully worked instance of the architecture we keep arguing for: an untrusted fast proposer, a cheap exact acceptance check, and a slow trusted fallback, with correctness resting only on the check. It shows that the proposer can be arbitrarily clever or wrong without touching the guarantee, and that the check can be proved sound once, independently of how candidates are generated. That is the verifier-economics shape behind B12 and verifier-gated repair. The limit is that FloatLib's check is complete (it decides Euclidean division exactly), whereas most physics checks are partial.

Second, our deterministic step checks rely on numerical entailment by random substitution, which runs in floating point with a tolerance. FloatLib is a reminder that the arithmetic itself carries assumptions. FMA versus separate rounding changes a result from -2^-18 to 0, posit rounding is not nearest-value, and flush-to-zero breaks exact subtraction. If we report numerical agreement as evidence, the precision, format, and tolerance belong in the assumption ledger (B11) rather than being treated as neutral. The proved rational exp/log enclosures and the idea of certifying the specification against an external oracle separately from certifying the implementation against the specification are reusable if we ever move a numerical oracle inside a Lean-based physics formalization, as in the Seiberg-Witten work. This paper does not show that such a move would be cheap.
