Citation: Zhang, S., Wang, Y., Liang, J., Shi, Y., Zeng, W., Wang, M., He, S., Xu, N., Ye, S., Cai, K., Gu, X. SWE-Explore: Benchmarking How Coding Agents Explore Repositories. arXiv preprint, 2026. https://arxiv.org/abs/2606.07297v1

## What this paper is about

SWE-bench and similar benchmarks reduce a coding agent's whole attempt at fixing a real GitHub issue to a single pass/fail number, which hides whether the agent actually found the relevant code, correctly diagnosed the bug, or wrote a bad patch despite finding the right evidence. This paper isolates just the "finding the relevant code" step — repository exploration — as its own measurable task: given an issue and a large real codebase, an explorer must return a ranked list of specific code line-ranges under a fixed budget, scored against a novel line-level ground truth that the authors derive automatically from the actual reading behavior of multiple independent agents that successfully solved the same issue, rather than from manual annotation.

## Extended summary

SWE-Explore is built from three existing repository-level sources (SWE-bench Verified, SWE-bench-Pro, SWE-bench Multilingual). An instance is retained only if at least two independent agent trajectories (from strong LLMs including GPT-5.4, Gemini-3-Pro, Sonnet-4.6, GLM-5.1, Kimi-K2.6) successfully resolved the underlying issue under the original executable harness; this yields 848 instances across 10 languages and 203 repositories (64.5% Python, the rest split across Go, JavaScript, Rust, Java, PHP, TypeScript, Ruby, C, C++). Ground truth is constructed by extracting every unambiguous file-line read action (editor views, cat/head/tail/sed reads, grep hits) from each successful trajectory, taking the file-wise line-level intersection across trajectories as a conservative "core context" candidate, then using an LLM-based refinement step to promote additional trajectory-specific reads when they are judged load-bearing for the issue, followed by a full manual audit of every promoted region against the issue and trajectories. The resulting ground truth averages 4.3 files, 4.7 regions, and 1,578 lines per instance, embedded in repositories averaging 759 files and 180K lines.

The task itself is format-agnostic: any system (sparse retriever, dense retriever, or full agentic explorer) just needs to return an ordered list of (file, line-range) regions, with no patch or repository-write access required. Metrics span three families: coverage/accuracy (line-level precision, recall, F1, plus coarser file-level and region-level hit rates that tolerate imprecise line boundaries), budget-aware ranking (a line-budgeted nDCG that penalizes a single verbose early region for exhausting the budget without proportional gain, plus "first useful hit," how early the first relevant line appears), and efficiency/noise (the fraction of predicted lines that are actually grounded evidence, and a region-level noise rate). To check these upstream metrics track real repair ability, the paper runs a one-time restricted-context validation: each explorer's output becomes the only visible repository content for a fixed coding-agent patcher, whose resulting patch is scored by the original SWE-bench harness — a design meant to isolate exploration quality from patch-synthesis skill, since the patcher scaffold and prompt are held fixed across all explorers. Across the 848-benchmark's shared n=150 correlation subset, Context Efficiency has the strongest overall (Pearson r=0.950) correlation with downstream resolve rate, Recall@100 the strongest rank-stable (Spearman rho=0.845) correlation, and HitFile/HitRegion/FUH also correlate strongly, while nDCG variants separate broad quality tiers well but order similarly-performing explorers less reliably; this analysis is used to justify a compact primary metric set (Precision, nDCG@500, HitFile, Context Efficiency) reported alongside conventional Recall/F1/noise diagnostics.

Fourteen explorers spanning four families (Oracle and Random bounds; sparse retrievers BM25/TF-IDF; a lightweight dense retriever, Potion; and nine agentic/localization systems — five general coding agents including Claude Code, Codex, OpenHands, Mini-SWE-Agent, AweAgent, plus four published academic localizers AutoCodeRover, LocAgent, OrcaLoca, CoSIL) are evaluated at a fixed budget of K=5 regions. Headline findings: every agentic explorer scores far above sparse/dense retrieval baselines, which remain close to Random — one-shot lexical or embedding retrieval is fundamentally insufficient for this task; nearly all non-oracle explorers show a striking asymmetry between high file-level hit rates (0.5-0.68) and low line-level recall (0.12-0.23), meaning agents reliably reach the right file but miss much of the specific evidence within it, a pattern the authors identify as the central bottleneck; swapping the underlying LLM backbone (holding the Mini-SWE-Agent scaffold fixed across GPT-5.4, GPT-5.4-mini, Kimi-K2.6, Sonnet-4.5, GLM-4.7, Gemini-3-Pro) shifts the operating point but not this file-vs-line asymmetry, meaning a stronger patching model alone does not resolve the exploration bottleneck; the five general-purpose coding agents cluster tightly together on nearly every metric despite differing substantially in implementation and harness complexity, suggesting a simple explorer interface can already expose most of the behavior a full production harness would show; and among the specialized academic localizers, only CoSIL (iterative code-graph search) meaningfully breaks the recall ceiling other localizers share, reaching by far the highest non-oracle line recall and F1, though at a higher noise cost from emitting whole-file regions. A controlled context-degradation experiment (exposing only an alpha% fraction of Oracle's core regions, versus that same alpha% padded back to full size with random non-core noise) finds missing core evidence is the dominant failure mode on an easier task subset — resolve rate stays flat through partial context and jumps sharply only once roughly 50-75% of core evidence is present — while moderate redundant/noisy padding is comparatively well tolerated once the core-evidence threshold is crossed, though it hurts substantially (7-9 percentage points) when core evidence is nearly absent; on a harder subset, context manipulation has a much narrower effect, suggesting that when an issue exceeds the patcher's underlying capability, better context alone cannot compensate. Authors' stated limitations: the benchmark covers only instances solved by at least one agent in the trajectory pool, so it is not representative of the full distribution of unsolved real-world issues; the trajectory-derived ground truth is an empirical approximation of necessary context rather than a proof that no other evidence could support a valid fix, since some valid solution paths may rely on different evidence than the ones observed; and the restricted-context protocol is explicitly framed as a one-time validation of the exploration metrics rather than a general measure of patch-generation ability. No funding is disclosed; code and the dataset are both publicly released.

## Learnings

The core methodological contribution — deriving line-level "necessary context" supervision from the intersection of independent successful agent trajectories, refined by an LLM-based promotion step for trajectory-specific-but-load-bearing reads, and finalized by full manual audit — is a directly transferable low-cost annotation technique for any agentic task where "what evidence was actually needed" is hard to specify a priori but recoverable after the fact from successful solution behavior; it sidesteps the inconsistency risk of manual annotation across hundreds of repositories and ten languages while still anchoring the target in genuinely observed, successful behavior rather than a single model's guess.

The budgeted-prefix nDCG design (an explorer's score is computed over the longest ranked prefix whose cumulative line count fits a fixed budget, rather than a fixed rank cutoff) is a specific, reusable evaluation-metric fix for any ranked-retrieval-under-resource-constraint setting: it directly penalizes a system that front-loads one large, verbose region, which a rank-based cutoff alone would not catch.

The central empirical finding — that current coding agents reliably localize the correct file (high HitFile) but systematically under-cover the specific lines within it (low line-level recall), and that this specific gap persists across every tested LLM backbone — is a transferable diagnostic distinguishing two capabilities usually conflated under "code localization": finding the right neighborhood versus exhaustively covering the evidence inside it. This reframes "better patching model" and "better exploration mechanism" as two different levers, with the paper's evidence pointing squarely at the second as the actual bottleneck.

The controlled context-degradation result — that missing essential evidence is a much sharper, threshold-like failure mode than moderate injected noise, at least once a baseline coverage level is reached — is a transferable design principle for any context-selection or retrieval-augmented system: it argues for prioritizing recall of essential evidence over aggressive precision-oriented filtering, since redundant-but-irrelevant content is comparatively well tolerated by modern patchers once the necessary evidence is present.

## Verification

The paper's verification design is one of its strongest features: rather than asserting that its chosen upstream metrics (precision, nDCG, hit rates, context efficiency) matter, it runs an explicit, controlled downstream validation — feeding each explorer's output as the only visible context to a fixed patcher and scoring the resulting patch with the original executable SWE-bench harness — and reports the actual Pearson/Spearman correlation between every candidate metric and this downstream resolve rate (Table 4), using that analysis to justify which metrics are kept as primary versus reported only as diagnostics. This is a genuine empirical validation of the benchmark's own construct validity, not an assumed one. The ground-truth construction itself layers three independent checks (cross-trajectory intersection, LLM-based load-bearing promotion, and full human audit of every promoted region), which is more rigorous than a purely automated pipeline. The main limitation is that no run-to-run variance is reported for the primary exploration-quality tables (Table 5, Table 6): each explorer appears to be evaluated once per instance, with no seeds, repeated trials, or confidence intervals, despite several of the reported gaps between explorers (e.g., the closely-clustered general coding agents in Sec. 4.3) being numerically small enough that variance would matter for confidently ranking them. A more structural verification concern is that the ground truth itself is derived partly from GPT-5.4's own successful trajectories (one of five trajectory-source models), while GPT-5.4 is also the backbone driving all agentic explorers in the main comparison table (Table 6) and one of the two downstream patchers used to validate the metrics (Table 3/4) — meaning the model whose behavior partly defines "correct" exploration is also the model being evaluated as an explorer and used to check whether the metrics are meaningful, an overlap the paper does not explicitly discuss or control for.

## Field context

SWE-Explore sits in the SWE-bench-derived ecosystem it reviews extensively (SWE-bench Verified, SWE-bench-Pro, SWE-bench Multilingual, Multi-SWE-bench, SWE-rebench) and the more specific "isolate a sub-capability of coding agents" niche it distinguishes itself from (ContextBench's human-annotated gold contexts, SWE-Pruner's context compression, SWE-ContextBench's experience reuse, Loc-Bench's file/function localization) — its own comparison table (Table 1) argues it is the first to combine executable grounding, multilingual coverage, line-level trajectory-grounded ground truth, and joint exploration-plus-repair validation in one benchmark. Its baseline pool overlaps directly with [reviews/2606.05405.md](2606.05405.md) (Agents' Last Exam), reviewed earlier in this batch, which evaluates several of the same general-purpose coding-agent harnesses (Claude Code, Codex, OpenHands) across a much broader set of professional domains beyond software engineering; both papers independently converge on a related structural finding — that different production coding-agent harnesses, despite differing considerably in implementation complexity, cluster tightly together in performance once a capable backbone model is held fixed (SWE-Explore's "general coding agents behave surprisingly similarly" finding in Sec. 4.3 mirrors ALE's finding that harness choice explains far less performance variance than backbone-model choice). This convergence across two independently-constructed benchmarks, using different tasks and metrics, is a reasonably strong cross-validated signal that current harness engineering has become a comparatively minor lever relative to the underlying model for at least this class of coding-agent evaluation.

## Critical discussion

The paper's central design choices are well justified and internally consistent: isolating exploration from patch synthesis is a genuine methodological advance over pass/fail benchmarks for diagnosing where a coding agent's effort actually fails, the trajectory-grounded ground-truth construction is a creative and reasonably rigorous solution to the problem of annotating "necessary context" at scale across ten languages without pure manual labor, and the explicit downstream-correlation validation (Table 4) is a real check on construct validity rather than an assumed one — a discipline not every benchmark paper in this space applies to its own chosen metrics.

The main limitation is a circularity the paper does not explicitly address: because the ground truth is partly derived from GPT-5.4's own successful trajectories, and GPT-5.4 also serves as the backbone for every agentic explorer in the main comparison and as a downstream patcher in the validation protocol, there is a structural overlap between the model that helped define correctness and the model being evaluated against it — this does not invalidate the qualitative findings (the file-vs-line recall gap, for instance, is consistent across every tested backbone including several that never contributed trajectories), but it does mean the specific numerical gap between, say, GPT-5.4-based explorers and other backbones should be read with some caution about self-consistency effects. A second limitation is the absence of any reported run-to-run variance in the primary results tables, which matters most for the paper's claim that the five general coding agents "behave surprisingly similarly" — without confidence intervals, it is not fully possible to distinguish genuine convergence from noise across explorers whose point estimates are numerically close. The benchmark's own stated scope limitation (only issues solved by at least one pooled agent are included, so unsolved or exploration-impossible issues are excluded by construction) is disclosed candidly and appropriately narrows the benchmark's claims to "quality of exploration among issues that are solvable at all" rather than a broader claim about repository understanding in general. What remains solidly supported: current agentic coding explorers form a clear, large tier above classical lexical/dense retrieval; the specific bottleneck limiting further improvement is line-level recall within an already-correctly-identified file rather than file-level localization itself, and this bottleneck is not resolved merely by swapping in a stronger backbone model; and missing essential evidence is a substantially more damaging failure mode for downstream repair than moderate irrelevant context, a finding independently corroborated by a controlled degradation experiment rather than inferred from the main correlational results alone.
